# Global rules (all projects)

## Where a new rule/lesson goes: skill → CLAUDE.md → project memory
CLAUDE.md is loaded in full, unconditionally, in every conversation in every project — its cost is fixed and permanent. A skill's body only enters context when the skill is actually invoked (only its name + one-line description sit in every conversation otherwise) — its cost is paid only when that phase of work is actually reached. Project memory is scoped to one project (and, more narrowly, one working-directory path — a worktree has a *separate* memory silo from its repo's primary checkout).

When something worth remembering comes up mid-task, place it in the first of these that fits, in order:
1. **A phase/domain skill**, if the rule is universal but only relevant during a specific kind of work (a ticket phase, a stack, a workflow step) — `product-ownership`, `worktree-manager`, `test-verification`, `finishing-a-development-branch`, a language/framework skill, etc.
2. **This file**, only if the rule is universal *and* applies regardless of what kind of task is underway (a safety rule, a platform quirk, a cross-cutting habit) — genuinely rare; most learnings fit a skill instead.
3. **Project memory**, if the rule is specific to one project's own facts, infrastructure, or the user's project-specific preferences.

**Why:** a batch of rules learned on subsplit tickets (manual-verification screenshots, `gh pr merge`'s classifier block, checking active sessions before assuming a worktree orphaned, Notion todo checkoff) initially landed in project memory, then got promoted wholesale into this file — only on review did it become clear most belonged one level down, in the skills that already govern those specific phases, so they're not a permanent tax on every unrelated conversation. Route new lessons to the right tier the first time instead of over-collecting here.

## Every project's CLAUDE.md must bootstrap this skills repo
Skills and these global rules live in the private repo `alessiogarifo92/claude-skills`, loaded from `~/.claude/` on a local machine. A **remote session** (Claude Code on the web, a cloud container, a GitHub Action) starts from an empty container with only the project repo cloned: `~/.claude/` has none of these skills, agents or rules (the folder may exist, empty of them), so none of this reaches the session — every rule below fails silently, and the session works as if this repo did not exist.

Each project's own `CLAUDE.md` therefore has to carry a bootstrap section that pulls this repo in, because the project's `CLAUDE.md` is the only thing a remote session loads on its own. Whenever a project's `CLAUDE.md` is created or edited, check that section is present and add it if missing — on a new project (see `project-lifecycle`) and equally on an existing one picked up for a ticket. The section instructs the session to attach `alessiogarifo92/claude-skills` (`add_repo`, clone, `register_repo_root`), run `bash <clone>/scripts/install.sh`, and — if a named skill is still not in the Skill list — Read `<clone>/<skill>/SKILL.md` directly, before starting work, and to say so in visible text if the attach fails, rather than proceeding rule-less.

- **Stale is as bad as missing.** An existing clone proves nothing about freshness: the bootstrap fetches and fast-forwards it, and each project commits the `templates/session-start-hook.sh` SessionStart hook, which does that automatically at every session start and prints the skills commit, whether it is behind, and the repo's visibility. A "BEHIND" line means update before any work.
- **The hook is added, not asked about.** Whenever this repo is attached alongside a project that lacks `.claude/session-start-hook.sh` + its `.claude/settings.json` entry, add both (copy `templates/session-start-hook.sh`; the JSON is in its header) and commit them on the session's working branch as the first change, without asking. Project hooks only load for the session's primary directory, so a multi-repo session relies on the environment's setup script (`templates/cloud-setup-script.sh`, set once by the user) to register the hook at user level.
- **The rule cannot live only here.** This file is loaded *because* the repo was attached; a rule inside it can never trigger its own attach. This section is the reminder to keep the bootstrap seeded in every project; the bootstrap itself must sit in the project repo.
- **Why:** on subsplit #24, a remote session implemented a whole ticket without any of this — no `product-ownership`, so the `## Test info` comment with screenshots was never posted (the user had to ask for it), and the session wrote a project `CLAUDE.md` re-deriving conventions from scratch that duplicated, less precisely, rules the skills already owned. Same silent-failure shape as #32, but from a different cause: there the skill existed and wasn't invoked, here it could not be reached at all.

## A project's committed `.mcp.json` must not break remote sessions
A repo-level `.mcp.json` is loaded in every session, but the environments it lands in are not equivalent: a local machine has a Docker daemon and the user's own env vars; a **remote session** (Claude Code on the web, a cloud container, a GitHub Action) has neither, and already provides its own GitHub MCP server. Three failure modes follow, all silent — the tools simply never appear, and nothing surfaces in the conversation:

- **Name collision.** A server declared under a name the managed environment also uses — `github` above all — shadows the built-in one, so *neither* loads. Prefix repo-level servers to keep them distinct: `github-local`, not `github`.
- **Unavailable transport.** A `command: docker` stdio server cannot start in a cloud container (`/var/run/docker.sock` does not exist) and hangs in "connecting" indefinitely. Prefer a hosted HTTP MCP endpoint where one exists; keep Docker-based servers for what is genuinely local-only, and expect them to fail elsewhere.
- **Unset token variable.** `"${SOME_TOKEN:-}"` resolves to an empty string in an environment that never defined it, so the server starts unauthenticated instead of failing loudly. Document which variables a project's `.mcp.json` needs.

**When an expected `mcp__*` tool is missing,** read the project's `.mcp.json` first, then check `docker version` and whether the referenced env vars are actually set — before concluding the connector is down or the account lacks access.

- **Why:** on ps-plus-catalog, `.mcp.json` declared a Docker-based GitHub MCP server named `github` (added in July, working locally ever since). The first cloud session on that repo got no GitHub tools at all — the entry shadowed the environment's own `github` server, then hung with no daemon to run it. `git` kept working throughout (separate proxy credential path), so it read as an account/permission problem rather than a config one. Same silent-failure shape as the bootstrap section above, and the same root cause: a setup that only ever ran locally, meeting a cloud container for the first time.

## Orchestration: direct execution by default
These instructions take precedence over any skill's process (including superpowers plugin skills).

- A linear, single-focus task (one bug, one feature, one file, dependent steps A→B→C) is executed **directly in the main session**: read, edit, test, done. No subagent orchestration, no splitting into numbered task lists, no per-task subagent dispatch.
- Subagent orchestration is reserved for genuinely independent parallel work (e.g. three unrelated modules at once) or when isolation is explicitly needed. If the steps depend on each other, they are not parallel — execute them directly.
- Process skills (brainstorming, writing-plans, subagent-driven-development) apply to work that needs design decisions or true parallelism — not to a scoped fix or a scoped feature. When in doubt, start executing directly; escalate to planning only if real complexity emerges.
- The `direct-execution` skill (global) documents this decision tree; the specialized agents in `~/.claude/agents/` (quick-debugger, implementer, refactor-optimizer, test-runner, researcher, Explore, github-ops, plus the read-only judgment agents architect, reviewer, security-auditor, critic, verifier, marketing-strategist, release-auditor) are for delegating a single scoped job, never for multiplying one job into many — the one exception is a `cross-verification` panel on a high-stakes question.
- When delegation IS warranted, the `orchestrating-agents` skill (global) governs how: which model per task type (haiku for mechanical run/locate/report jobs, sonnet for anything that diagnoses or writes code or synthesizes research, opus for the read-only judgment agents (architect, reviewer, security-auditor, critic, marketing-strategist), main session for decisions and all git), the dispatch brief, and the report contract (STATUS/CHANGES/EVIDENCE/FINDINGS/OPEN).
- **End-to-end or unattended runs** go through the `autonomous-workflow` skill (for a brand-new project `project-lifecycle` is still invoked first, per the rule above): it owns the stage map (which skill, agent, model and gate per stage) and which decisions always stop for the user. Autonomy removes small questions, never the hard gates (user decisions, spend, publishing, push/merge before the manual check, deploy, destructive operations).
- **High-stakes decisions and results** (architecture, security, data migration, deploy, public copy) get independent parallel agents compared against each other via the `cross-verification` skill — blind first round, a critic, decision on evidence. Linear low-stakes work never does; `direct-execution` stays the default.
- **Verification gate**: every agent report is a claim, not a fact. Before starting the next phase or dispatching the next agent, the main session verifies the report — check the diff against CHANGES, re-run the narrowest test against EVIDENCE, spot-check a load-bearing research claim. Never build phase N+1 on an unverified phase N; never route around a `blocked` status.

## Always enter through `project-lifecycle` for a new application/project
Whenever a request is to build a new app/project from scratch, or to evaluate one end-to-end (not a single ticket in an already-running project), invoke the `project-lifecycle` skill as the very first action — before drafting tickets, before architecture, before any code. Never let the request implicitly skip straight to ticket-drafting or implementation.

- **Why:** `project-lifecycle` sequences the whole arc (idea → stack/cost → architecture → design → tickets → implementation → deploy) and each phase gate — including the Design UI/UX gate below — only fires if the skill that owns it was actually loaded. On a prior project, build tickets were drafted and implemented straight from the idea, skipping the phase sequencing entirely; the Design UI/UX gate existed at the time but never had a chance to catch the gap, because the skill carrying it was never invoked. The rule below is one symptom of that same root cause — this rule fixes the cause, not just that symptom.
- **How to apply:** treat "has `project-lifecycle` been invoked yet" as the default check for any new-project request, the same way you'd check whether a file has been read before editing it. If the user jumps straight to "make ticket X" on a project whose earlier phases (idea/stack/architecture/design) were never confirmed, flag the gap and offer to backfill the missing phase before drafting the ticket, rather than drafting it against undecided assumptions. Map "roles" the user asks for (product owner, architecture, cost research, frontend, backend, QA, marketing, deploy) to this skill's existing phases and their constituent skills (`product-ownership`, `market-analyst`, `architecture-review`/`principal-engineering-core`, `impeccable`, language-specific backend skills, `test-verification`/`test-driven-development`, `product-marketing-strategist`, `security-review`) rather than creating new dedicated agents per role — per the direct-execution default above, agents stay reserved for genuinely parallel/isolated work, not for process/knowledge that a skill already covers.

## Never skip a Design UI/UX phase before development
When a project's own plan defines a distinct Design UI/UX phase (mockups, palette, typography, component design, or an approved reference site to match) ahead of a development/build phase, do not start writing theme/frontend/UI code until that design phase has a concrete deliverable — a mockup, a style guide, or an explicit reference to build against.

- Before executing build/implementation tickets, check whether the project's own plan places a design phase earlier in the sequence. If it does and no design deliverable exists yet, stop and flag the gap to the user before proceeding with more build tickets — don't silently keep executing tasks that assume a design outcome that hasn't happened.
- **Why:** on DamianoGuideSite, a technical build plan correctly marked visual design "out of scope" for its own narrow scope, mirroring the project's broader phase plan (a Design UI phase listed before the Sviluppo/build phase in `strategia-progetto.md`) — but the build phase started without that design phase ever producing a deliverable. Several build tickets shipped working code against an unstyled default theme with no design direction, which only surfaced when the user compared the live result to a reference site they had in mind and it looked nothing like it. The rework cost is the same whether it's caught on ticket 1 or ticket 7 — catching it earlier is strictly better.
- **How to apply:** if the user hands over a reference site, mockup, or style direction mid-build (i.e., after the gap is discovered), treat it as the missing Design UI-phase deliverable: capture it in project memory, and if the project tracks work as tickets/phases, offer to open the design phase as its own ticket rather than absorbing style changes ad hoc into unrelated build tickets.
- **Study/investigate before designing, then use `/design` for multiple comparable options.** Before producing the Design UI/UX phase's own deliverable, do the study/investigation groundwork first: read the project's existing plan/docs (e.g. `strategia-progetto.md` or equivalent), any reference site or brand/palette signals the user already gave, and the pages/content the UI actually needs to cover — the deliverable should be grounded in that context, not generic. Then, where the deliverable is visual (UI mockups, screen flows, landing pages), use the `design` skill (`/design`) rather than describing the design in text or jumping to frontend code — it publishes a multi-artboard canvas the user can view and edit. Generate more than one distinct visual direction in that canvas so there's something to actually compare and choose between, not a single take to accept or reject outright.
  - **Why:** a text description of a design, or a single take, forces the user to imagine the result or accept/reject it blind; a canvas with real visual options lets them compare and pick, which is the actual point of having a design phase before committing to frontend code.

## Commands handed to the user
Any command the user is asked to run must use absolute paths, or explicitly state the directory (`cd /path && ...`) and the environment (host shell vs a specific Docker container) to run it in. Never hand over a bare relative path.

## Announce agent model/effort
Every time the Agent tool is used (any subagent_type — built-in or custom), state in visible text which model it runs on (its frontmatter `model:` field, or the `model` override passed to the call) and its effort/reasoning level if one applies (e.g. a `low`/`medium`/`high` review effort). Announce this at launch time, not only after the result comes back — a one-line note is enough (e.g. "Lancio `github-ops` (modello haiku).").

## Sudo and installing missing tools
Ask the user for the OK before any `sudo` or tool installation. Once the OK is given, try running the command yourself; hand it to the user for manual execution only when it genuinely cannot be run (needs an interactive password/tty, sandbox denial, missing permissions) — and say that's the reason.

## Every implementation ticket ships with unit tests, not just a Playwright/manual pass
Playwright (and the manual-verification handoff `test-verification` defines) proves the feature works end-to-end on a real running stack; it does not substitute for unit-level coverage. For any implementation ticket — feature, bug fix, or refactor that changes behavior, regardless of ticket type — write unit tests for the changed logic in addition to the browser/manual checks, before considering the ticket done.

- Specifically cover error paths and edge cases (invalid input, failure/exception branches, boundary and empty/null cases) — not just the happy path a Playwright walkthrough already exercises. A ticket whose only test evidence is "the page loaded and nothing errored" is missing the unit layer.
- This governs *coverage*, not write-order — `test-driven-development` still decides whether the test is written before or alongside the code. Either way, the ticket isn't done when Playwright is green if the underlying logic has no unit tests behind it; `test-verification` still picks the narrowest meaningful set and runs it via `test-runner`.
- If the project has, or is being set up with, a CI/CD pipeline, make sure the new unit tests are wired into whatever coverage tooling that pipeline already runs (or is being configured to run) — the point is that they show up in the pipeline's coverage report, not just pass locally once and never execute again. Don't bolt on a new coverage tool/config to a project that has none unless the user asks for it; if a pipeline already tracks coverage, extend it.
- **Why:** a green Playwright/manual pass only proves the wiring between UI and backend didn't break on the scenario walked through — it says nothing about untested branches inside the changed logic, and gives no lasting signal once the change ships, whereas unit tests keep re-verifying that logic on every future change and (with coverage wired in) surface regressions in CI before a human ever has to click through the UI again.

## Never wipe shared DB data while another ticket is in progress
Destructive operations on a shared database — resetting/seeding fixtures, `migrate:fresh`, wiping tables, deleting mock data inserted for a manual check (`test-verification`) — may run only when no *other* ticket carries the `in progress` label: check `gh issue list --label "in progress"` first (in a remote session, where `gh issue ...` is GraphQL and gets a 403: `gh api "repos/{owner}/{repo}/issues?labels=in%20progress" --jq '.[].number'`), excluding your own ticket. This applies exactly as much to automated test runs (the `test-runner` agent, CI-style suites) as it does to the manual-verification stack — it generalizes `test-verification`'s "one environment at a time" from "don't run two manual checks at once" to "don't destroy data another ticket might still be reading, even from an unattended run".
- If another ticket is in progress, don't destroy shared data — either wait for it to close, or use a solution that doesn't require destruction: data scoped/namespaced to your own ticket, a transaction that rolls back instead of committing, or a separate schema/database reserved for automated tests.
- **Why:** without this check, one agent's fixture reset or table wipe can corrupt another agent's test that's mid-flight on the same shared DB, even though neither session touched the other's code.

## One git worktree per ticket
Create the worktree only when code in the repo is actually about to be written or modified — not as a reflexive first step on every ticket, and not for tickets that never touch the repo (a research ticket whose deliverable is an issue comment, for example). When that moment arrives, never work directly on the default branch of the primary checkout — use an isolated worktree, via the global `worktree-manager` skill (`~/.claude/skills/worktree-manager/scripts/worktree.sh`). This is the same convention and the same script in every project — present and future — not something to reinvent or copy per-repo:

- `worktree.sh start <issue> [slug]` creates + locks `.claude/worktrees/<slug>` on branch `worktree-<issue>-<slug>` (ensuring that directory is git-ignored) and applies the `in progress` label to the issue. Call it right before the first file gets touched, not at ticket pickup — research/investigation work (reading code, drafting a report, grounding a ticket) doesn't need it.
- A ticket that stays research-only (report lands as an issue comment, no repo commit) still gets picked up and marked in progress, just without a worktree — label it directly: `gh issue edit <n> --add-label "in progress"` (remote: `gh api -X POST "repos/{owner}/{repo}/issues/<n>/labels" -f "labels[]=in progress"`). If the research later produces a `docs/` file that gets committed, that commit is code work — create the worktree at that point, not before.
- Two sessions must never write to the same branch. A locked worktree belongs to another session — do not touch it; unlocking is the owner's explicit handoff step.
- After the branch merges: `worktree.sh cleanup` unlocks/removes the merged worktree and branch, and clears orphaned worktree directories; the remote branch still needs `git push origin --delete` separately.
- If a repo genuinely can't use the script (no `gh` auth, unusual branch layout), fall back to the convention manually — same naming, same lock discipline — but that's the exception, not the default.

## Remove the "in progress" label when a ticket closes
GitHub does not strip labels on close automatically. Whenever a ticket/issue closes — for any reason and by any path (fix shipped, research report delivered, closed as duplicate/wontfix/not-planned, superseded by a different commit or PR) — remove the `in progress` label as part of that same closing action, not as a follow-up to remember later: `gh issue close <n> --comment "..."` paired with `gh issue edit <n> --remove-label "in progress"` (or the single combined call if the `gh` version supports it). In a remote session (`gh issue ...` is GraphQL, blocked with a 403) close with the GitHub MCP `issue_write` (`state: closed`, `state_reason`) and remove the label with `gh api -X DELETE "repos/{owner}/{repo}/issues/<n>/labels/in%20progress"`. This applies uniformly regardless of ticket type; don't treat it as specific to the bug/implementation workflow.

## Restore the stack to main when a ticket closes
If the running stack was swapped to serve this ticket's worktree for manual verification (per `test-verification`'s "Browser checks" — real data, standard ports, one environment at a time), swap the code-serving layer back to the primary checkout on its default branch (typically `main`) as part of the same closing action — never leave it pointed at a just-closed ticket's worktree. Do this before running `worktree.sh cleanup`: cleanup removes the worktree directory/branch, and a stack still pointed at it will break instead of falling back to anything. Applies regardless of why the ticket closed (merged, superseded, wontfix).

Applies the same way when the code-serving layer is a directly-run dev server rather than a container/bind-mount swap (e.g. Expo Go's `expo start`): stop the process running from the worktree and restart the same command from the primary checkout on the same port, instead of leaving a just-closed ticket's dev server as the one actually being served.

## Invoke `product-ownership` itself at ticket pickup, not only `worktree-manager`
At the pickup point of any ticket, invoke the `product-ownership` skill itself — not only `worktree-manager` (which only covers the mechanical branch/worktree part). Skill instructions only enter context when the skill is actually invoked; calling one narrow skill doesn't pull in a broader one that happens to reference it.

- **Why:** on subsplit ticket #32, only `worktree-manager` was invoked at pickup. `product-ownership`'s "Recording the check" section (the `## Test info` comment + screenshot convention) was never loaded into context as a result, so the manual-verification handoff was improvised in chat instead of following the documented process — the rule existed the whole time, it just was never in context when it mattered.
- **How to apply:** treat "did I invoke `product-ownership` yet" as a pickup checkpoint, the same way "is the in-progress label on" already is. The detailed rules that used to live here directly (Test info comments, private-repo screenshot links, checking active sessions before treating a worktree as orphaned, the `gh pr merge` classifier block, Notion todo checkoff) now live inside the skills that actually govern those phases — `product-ownership`, `worktree-manager`, `finishing-a-development-branch` — precisely so they're only paid for in context when that phase is actually reached, instead of sitting in every conversation regardless of task.
